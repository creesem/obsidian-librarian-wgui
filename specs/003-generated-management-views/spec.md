# Feature Specification: Generated Management Views

**Feature Branch**: `codex/work-management-phase-3`

**Created**: 2026-10-03

**Status**: Draft

**Input**: User description: "Render the Phase 2 read-only reviews into reproducible
Markdown views under `90_Staging/Views/`, as the first (explicit, staging-first,
containment-tested) `obsidian_operator` write path. No canonical note is ever
created, moved, modified, or deleted."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Preview Views Without Writing (Priority: P1)

A user renders the management views and reads them on stdout. Nothing is written.

**Why this priority**: The first write path must be safe to explore; preview is the
default and proves the content before any file appears.

**Independent Test**: Run `view render --all` against a fixture vault, assert the
six view documents appear on stdout, and assert every vault file is byte-unchanged.

**Acceptance Scenarios**:

1. **Given** a fixture vault with operational entities, **When** the user runs
   `view render --all`, **Then** Today, Projects, Team, Tickets, Waiting, and
   Manager Review documents are printed and no file is created.
2. **Given** `view list`, **Then** the available view names are listed without writing.

---

### User Story 2 - Write Views Safely (Priority: P2)

A user writes the views under `90_Staging/Views/`, with provenance frontmatter and
overwrite protection, without touching canonical notes.

**Why this priority**: This is the first operator write; containment and explicit
opt-in are the whole point.

**Independent Test**: Run `view render --all --write`, assert each file exists under
the views root with generated frontmatter, assert canonical entity files are
byte-unchanged, and assert a second write without `--force` is refused.

**Acceptance Scenarios**:

1. **Given** `--write`, **When** rendering completes, **Then** each view is written
   under `90_Staging/Views/` with `type: view`, `generated: true`, `generator`,
   `view`, `generated_at`, `reference_date`, `source_count`, and `sources`.
2. **Given** an existing view file, **When** rendering without `--force`, **Then**
   the write is refused and the existing file is unchanged.
3. **Given** `--force`, **When** rendering, **Then** the file is overwritten and the
   command reports it as overwritten.
4. **Given** an `--out` path outside the vault, or containing `..`, or absolute,
   **When** rendering with `--write`, **Then** the write is refused.

---

### User Story 3 - Reproducible Output (Priority: P3)

A user regenerates views with a fixed reference date and timestamp and gets
byte-identical files.

**Why this priority**: Reproducibility makes generated views trustworthy and diffable.

**Independent Test**: Render twice with the same `--today` and `--generated-at`; assert
byte equality.

**Acceptance Scenarios**:

1. **Given** fixed `--today` and `--generated-at`, **When** rendering twice, **Then**
   output is byte-identical.
2. **Given** no `--generated-at`, **Then** the current UTC time is used (non-reproducible
   by design, but the only non-deterministic field).

---

### Edge Cases

- Empty vault (no entities): views render with zero items, not an error.
- Vault path does not exist.
- `--out` resolves outside the vault via symlink or `..`.
- View file exists but is not generated by the operator (no generated frontmatter):
  still overwrite-protected unless `--force`.
- `--today` unparseable.
- `--all` combined with a specific view name.
- Unknown view name.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide `view list` (names only) and `view render <name>|--all`.
- **FR-002**: `view render` MUST write nothing unless `--write` is passed; without it, output goes to stdout.
- **FR-003**: Writes MUST be confined to a views root, default `<vault>/90_Staging/Views`, resolved under the vault; absolute paths and `..` MUST be refused.
- **FR-004**: Existing files MUST be refused unless `--force` is passed explicitly.
- **FR-005**: Every written view MUST carry generated-provenance frontmatter (`type: view`, `generated: true`, `generator: obsidian-operator`, `view`, `generated_at`, `reference_date`, `source_count`, `sources`).
- **FR-006**: View content MUST be derived only from the Phase 2 review functions (`attention_items`, `build_project_review`, `build_person_workload`); no new business rules.
- **FR-007**: Output MUST be deterministic given fixed `--today` and `--generated-at`.
- **FR-008**: The command MUST report the change set (paths, created/overwritten) when writing.
- **FR-009**: The system MUST NOT create, move, modify, or delete any canonical/trusted note.
- **FR-010**: The system MUST NOT call external APIs, LLMs, embeddings, OCR, MCP tools, or Agents SDK runtime.
- **FR-011**: `obsidian_operator` MUST continue to import only `obsidian_inventory`.
- **FR-012**: The view set MUST be exactly: `today`, `projects`, `team`, `tickets`, `waiting`, `manager-review`.

### Key Entities

- **Generated view**: a reproducible Markdown document with generated-provenance frontmatter and a `sources` list of contributing entity paths.
- **View definition**: a stable name, output filename, and a builder that produces the body from the operator index and reference date.
- **Write result**: target path plus created/overwritten status.

### Safety and Provenance Requirements *(mandatory for this repository)*

- **Write boundary**: `<vault>/90_Staging/Views/` by default; `--out` may relocate but MUST remain under the vault. No canonical folder is ever a write target.
- **Overwrite policy**: refused by default; `--force` is explicit and reported.
- **Source provenance**: each view lists the entity paths it was generated from and stamps `generated_at`, `generator`, `reference_date`.
- **Uncertainty handling**: unresolved links and validation issues already surface in Phase 2 content; views do not invent data.
- **Review report**: the command prints created/overwritten paths and counts.
- **Constitution gate (Phase VI)**: this is a new write path, so it is specified before implementation and covered by containment tests.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Without `--write`, fixture tests show zero file changes.
- **SC-002**: Containment tests fail closed for absolute paths, `..`, and out-of-vault `--out`.
- **SC-003**: Overwrite is refused without `--force`; with `--force` the file is replaced and reported.
- **SC-004**: With fixed `--today`/`--generated-at`, two renders are byte-identical.
- **SC-005**: Canonical entity fixture files are byte-unchanged after any view command.
- **SC-006**: The operator import-boundary test still passes (only `obsidian_inventory`).
- **SC-007**: Generated views under `90_Staging` do not appear as operator entities in a subsequent `vault`-scope index.

## Assumptions

- Generated views are derived state and never canonical; regeneration replaces them.
- Writing under `90_Staging` keeps views out of the operator's `vault`-scope index automatically.
- The operator keeps a small local containment helper rather than importing `obsidian_librarian.vault`, preserving the dependency boundary.
- No database; Markdown remains the format.
